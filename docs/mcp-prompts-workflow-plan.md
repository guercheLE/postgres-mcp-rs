# MCP prompts: guided PostgreSQL catalog workflows

## Context

`postgres-mcp-rs` exposes exactly 4 MCP tools -- `search`, `get`, `call`,
`execute_sql` ([src/core/mcp_server.rs](../src/core/mcp_server.rs)) --
backed by an embedded, per-PostgreSQL-version catalog of `pg_catalog`/
`information_schema` operations. This is 6 separate catalogs, one per
supported PostgreSQL version ([src/data/store.rs](../src/data/store.rs)):
`mcp_store.db.zst` = version `18` (default), plus `_v14`, `_v15`, `_v16`,
`_v17`, `_v19beta2`. The default catalog has exactly 500 rows: 346
`call_pg_catalog_*` operations (POST, invoking `pg_catalog` functions), 64
`read_information_schema_*` operations (GET, SQL-standard views), and 90
`read_pg_catalog_*` operations (GET, PostgreSQL-native catalog/stat views).

Some catalog views were split or renamed across the 6 supported versions
(e.g. `pg_stat_checkpointer` is new in PostgreSQL 17, carrying fields that
previously lived in `pg_stat_bgwriter` in 14-16) -- exactly the kind of
cross-version drift that means workflow prose must never hardcode a
response field name from memory. It must always tell the calling LLM to
call `get` on whatever operationId `search` resolves to and read the
*current* schema from that response.

This flat 4-tool surface leaves all sequencing knowledge -- e.g. "there is
no catalog operation for `EXPLAIN`/`VACUUM`/`ANALYZE`/`GRANT`/DDL, so those
have to go through `execute_sql` instead" or "don't report a role's grants
as the full picture without also checking row-level security policies" --
entirely up to whichever LLM is driving the client, re-derived from scratch
every session.

The goal is to add an MCP **prompts** capability: a master "menu" prompt
plus one prompt per logical PostgreSQL diagnostic/administrative domain
(schema introspection, roles & permissions, sessions & locks, replication &
WAL, vacuum & maintenance, query performance, server health & config,
extensions & FDW, ad hoc data profiling). Each prompt returns instructional
prose that guides the calling LLM through a domain's task step by step --
asking for missing parameters, gating progression until a step's goal is
actually verified (not just attempted), calling out where steps are
independent and can run in parallel or be delegated, and always describing
catalog operations by capability ("search for how to list a table's
indexes") rather than a specific `operationId` or assumed response shape.

The sibling project `jira-dc-mcp-rs` (same "mcpify" generator, same
flat-tools-over-an-embedded-catalog architecture) already solved this exact
problem the same way; this plan replicates its pattern (module layout,
`render_context_header` helper, delegation guidance) verbatim where it's
domain-agnostic, and adapts it where PostgreSQL's shape differs from
Jira's -- most importantly, this server's extra `execute_sql` tool, which
`jira-dc-mcp-rs` has no equivalent of.

This repo is generated output from `mcpify` (`src/core/mcp_server.rs`'s own
banner: "generated by mcpify. Do not hand-edit."; the README notes the
PostgreSQL-native dispatcher itself already required hand-adaptation after
generation, with the same re-apply-after-regeneration caveat). This plan
accepts that same, already-established risk: a future `mcpify` sync could
overwrite this feature's wiring in `mcp_server.rs`/`lib.rs` unless it's
later upstreamed into the generator itself.

The mechanism is already available for free: this crate's `rmcp = "2"`
dependency resolves to **rmcp 2.2.0** (`Cargo.lock`, confirmed identical to
`jira-dc-mcp-rs`'s own lockfile), whose `macros` feature (enabled by
default) ships `Prompt`, `PromptArgument`, `PromptMessage`,
`GetPromptResult`, `#[prompt_router]`, `#[prompt]`, `#[prompt_handler]` --
mirroring the `#[tool_router]`/`#[tool]`/`#[tool_handler]` pattern
`src/core/mcp_server.rs` already uses for `search`/`get`/`call`/
`execute_sql` almost exactly. No Cargo.toml change is needed. No MCP-prompts
capability exists anywhere in this repo before this change (`enable_prompts()`
is never called; grepping `workflow`/`prompt` across `src/`/`docs/` turns up
nothing but unrelated CI `.github/workflows/*.yml` files).

## Approach

### File layout

Prompt code is kept entirely separate from tool code: all prompt logic
lives in a new `src/prompts/` module, distinct from `src/tools/` (which
holds `search`/`get`/`call`/`execute_sql`'s business logic). The
`#[prompt_router]`-decorated `impl McpifyServer` block goes in
`src/prompts/router.rs`, never in the same file as the existing
`#[tool_router]`-decorated block. `src/core/mcp_server.rs` itself is
touched only for the minimal wiring a single `ServerHandler`/struct
necessarily requires -- the new struct field, the stacked handler macro,
and the `.enable_prompts()` capability flag -- no prompt method bodies or
prompt-specific logic are added there.

```
src/prompts/
  mod.rs                        // arg structs + render_context_header() helper (+ its own unit tests)
  router.rs                     // second `impl McpifyServer` block, #[prompt_router]-decorated
  content/
    master.md
    schema_introspection.md
    roles_permissions.md
    session_locks.md
    replication_wal.md
    vacuum_maintenance.md
    query_performance.md
    server_health_config.md
    extensions_fdw.md
    data_profiling.md
```

Instructional prose lives in `.md` files pulled in via `include_str!`, not
inline Rust string literals -- this follows the pattern the crate already
uses for large embedded assets (`data/store.rs`'s `include_bytes!` per
version `.db.zst`, `src/validation/validator.rs`'s equivalent for schema
JSON). Anything that varies per-invocation (which optional arguments the
caller already supplied) is rendered separately in Rust as a short "Context
already provided" header and prepended to the static markdown body -- no
template-substitution engine needed.

New hand-authored files do **not** carry the "generated by mcpify. Do not
hand-edit." header every other `.rs` file has -- that claim would be false
for this module.

### `McpifyServer` changes

Add a `prompt_router` field next to the existing `tool_router`, initialized
the same way in `new()`; stack `#[prompt_handler(router =
self.prompt_router.clone())]` with the existing
`#[tool_handler(router = self.tool_router.clone())]` on `impl ServerHandler`;
add `.enable_prompts()` to the capabilities builder. `PromptRouter<S>` is
`Clone`, so the struct's `#[derive(Clone)]` is unaffected, and
`McpifyServer::new(...)`'s public signature is unchanged -- its only two
call sites (`main.rs`, `http/server.rs`'s per-session factory) need no
changes.

### Prompt inventory

| name | description | arguments |
|---|---|---|
| `postgres` | Master index; menu + goal-based routing | `goal` |
| `postgres-schema-introspection` | Tables, columns, constraints, indexes, views, materialized views, sequences | `schema_name`, `table_name` |
| `postgres-roles-permissions` | Roles, membership, object grants, row-level security | `role_name`, `schema_name`, `table_name` |
| `postgres-session-locks` | Active sessions, blocking chains, locks, cancel/terminate | `pid`, `database_name` |
| `postgres-replication-wal` | Replication status, slots, publications/subscriptions, WAL lag | `slot_name`, `publication_name` |
| `postgres-vacuum-maintenance` | Autovacuum/analyze health, manual VACUUM/ANALYZE | `schema_name`, `table_name` |
| `postgres-query-performance` | Is it running now, EXPLAIN plan, index usage | `query_text`, `table_name` |
| `postgres-server-health-config` | `pg_settings`, bgwriter/checkpointer/archiver stats, backups | `setting_name` |
| `postgres-extensions-fdw` | Installed/available extensions, FDW objects | `extension_name`, `server_name` |
| `postgres-data-profiling` | Ad hoc row-level querying via `execute_sql`, safely | `table_name` |

Every argument is `Option<String>`, never `required: true` -- for the same
reason `jira-dc-mcp-rs` made this choice: MCP prompt arguments are
conventionally collected up front by whatever UI a client renders, not well
suited to values that only become known partway through a guided flow, and
a strict client could refuse `prompts/get` entirely until a required field
is filled. Pushing "ask if missing" into the instructional prose instead of
transport-level required-argument validation is what makes this work
uniformly for agentic clients that never populate prompt arguments at all,
and interactive ones whose humans do.

### The two-execution-path rule (specific to this server; no jira-dc-mcp-rs equivalent)

Every prompt must distinguish which of this server's two live-execution
paths applies:

- **`search` -> `get` -> `call`** whenever a catalog operation exists --
  pre-validated against a known input/output JSON Schema.
- **`execute_sql`** only when no catalog operation covers the need.
  Confirmed by direct inspection of the decompressed default catalog: there
  is **no** operationId for `EXPLAIN`, `VACUUM`, `ANALYZE`,
  `GRANT`/`REVOKE`, any DDL (`CREATE`/`ALTER`/`DROP`/`CREATE EXTENSION`), or
  `pg_stat_statements` (a contrib extension's view, not a built-in catalog
  object) -- these are SQL commands, not catalog functions, so they can
  only be reached through `execute_sql`.

Every sub-workflow with such a case says so explicitly and gates on it:
identifiers (table/column/role names) can't be bound as `execute_sql`
parameters (only values can) and must be validated against
`information_schema` before being interpolated into SQL text; `EXPLAIN
ANALYZE` actually executes the statement, so non-`SELECT` statements need a
rollback-able transaction wrapper; and every write path re-reads the
relevant catalog view afterward to confirm the change actually took effect,
rather than trusting a non-error response alone.

### The agnostic-phrasing rule (applies to every prompt)

Every operation reference in every `content/*.md` file is phrased as a task
to search for, never as a specific operationId -- e.g. "search for how to
list a table's indexes," not "call `read_pg_catalog_pg_indexes_...`." This
is required by the same version-drift reasoning `jira-dc-mcp-rs` documented
for its own 6 catalogs: this server also embeds 6 PostgreSQL version
catalogs (14 through 19beta2), and at least one confirmed structural
difference exists between them (`pg_stat_checkpointer` did not exist before
PostgreSQL 17). Phrasing every step as a natural-language search query,
followed by "read the schema `get` returns before relying on any field name
in it," keeps every prompt correct regardless of which of the 6 catalogs is
active.

### Content size and token economy

MCP's two-phase discovery model bounds most of the cost: `prompts/list`
returns only `name` + `description` + `arguments` for all 10 prompts (a few
lines each); `prompts/get` is per-prompt and on-demand. Individual
`content/*.md` files target roughly 40-120 lines, proportional to the
domain's real complexity -- `master.md` stays a lean menu (one line per
sub-workflow plus routing/delegation guidance); compound, multi-step,
gated domains (`vacuum_maintenance.md`, `query_performance.md`,
`roles_permissions.md`) run toward the long end; narrower domains
(`extensions_fdw.md`) stay short.

## Critical files

- `docs/mcp-prompts-workflow-plan.md` (this file)
- [src/core/mcp_server.rs](../src/core/mcp_server.rs) -- struct field,
  macro stacking, capabilities, import, `.with_instructions(...)` text
- [src/lib.rs](../src/lib.rs) -- `pub mod prompts;` declaration
  (alphabetically between `http` and `services`)
- `src/prompts/mod.rs` -- argument structs, `render_context_header` helper
  + its own unit tests
- `src/prompts/router.rs` -- the `#[prompt_router]`-decorated
  `impl McpifyServer` block, one method per prompt-inventory row above
- `src/prompts/content/*.md` (10 files) -- one per prompt
- `tests/prompts_workflow.rs` -- protocol-level `prompts/list`/
  `prompts/get` integration tests, kept out of `src/core/mcp_server.rs`'s
  existing `#[cfg(test)] mod tests` entirely

## Verification

- `cargo build` / `cargo test` from the repo root.
- **Prompt tests stay physically separate from tool tests** -- nothing
  prompt-related is added to `src/core/mcp_server.rs`'s existing
  `#[cfg(test)] mod tests` (which stays scoped to `search`/`get`/`call`/
  `execute_sql`, unchanged except that its own
  `server_info_advertises_the_generated_tool_surface` test still passes
  since `.enable_tools()` and the "search, get, call" substring in
  `with_instructions` are both preserved). Two separate test locations
  instead:
  - **`tests/prompts_workflow.rs`** -- protocol-level tests against the
    crate's public API (`postgres_mcp::core::mcp_server::McpifyServer`, an
    `rmcp::ClientHandler` stub, `tokio::io::duplex`, the same pattern
    `mcp_server.rs`'s own `mcp_protocol_routes_all_four_tools` test uses,
    promoted to its own file/compilation unit): `prompts/list` shape (all
    10 names, arguments all-optional), `prompts/get` round-trips for
    `postgres` (mentions every sub-workflow) and one domain prompt with
    partial arguments (echoes supplied values, lists missing ones), and a
    `info.capabilities.prompts.is_some()` assertion.
  - **`src/prompts/mod.rs`**'s own `#[cfg(test)] mod tests` -- pure unit
    tests for `render_context_header` (empty, all-supplied, all-missing,
    mixed).
- Manual smoke check: run the server over stdio and issue `prompts/list`
  then `prompts/get` for `postgres` and at least one domain prompt to
  confirm the rendered header + markdown body reads naturally end-to-end,
  not just structurally valid per the automated tests.
